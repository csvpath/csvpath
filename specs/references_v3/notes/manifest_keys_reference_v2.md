# Manifest Keys Reference

Seven manifest schemas, confirmed directly against each registrar's/listener's
own `metadata_update()` (not assumed) as of 2026-08-06. Each table lists every
key that schema actually writes, in write order. The Optional column marks a
key that is only written under some condition, not on every entry, and is
blank otherwise. The References v3 Function column names whatever v3
function already gives access to that key's value today, and is blank when
none does.

For tables 1, 3, and 5 (the three manifest.json files an existing
`ReferenceFinder3` actually reads), that column currently reads `:manifest()`
across every row, because that function returns the whole entry as one dict —
none of these keys has a dedicated, single-field accessor yet. Tables 2, 4,
and 7 are not read by any references-v3 finder at all today (table 7 is read
internally for run discovery, not exposed as a value). Table 6 is read
internally for `run_uuid`/`uuid` navigation, also not exposed as a value.
Finding the minimum set of dedicated field-accessor functions to fill in this
column is exactly the first open work item this catalog is feeding into.

This is a description-of-what-exists document, independent of any decision
about which keys should become references-v3 functions — that's a separate,
later exercise built on top of this catalog.

## 1. Named-File Manifest (per named-file)

`csvpath/managers/files/file_registrar.py` — one flat, append-only array per
named-file, one entry per registered version. This is the manifest
`FilesReferenceFinder3`/`:manifest()` actually reads today.

| Field | Optional | References v3 Function | Description |
|---|---|---|---|
| type |  | :manifest() | File extension. E.g. `csv`, `xlsx`, etc. |
| reference |  | :manifest() | A complete unique reference to a version of a registered file. This is as exact as providing the UUID for the purpose of obtaining the registered bytes. However, because it is the fingerprint of the bytes, and we allow the same bytes to be registered at different paths within the named file, the reference is not necessarily to the same registration event as produced the fingerprint. In practice this distinction rarely make a difference. And the benefit of using the fingerprint is that the fingerprint can be constructed using the bytes, even if it is not certain where those bytes may have been registered within the named-file. In general, be confident that you will get the correct bytes, but mindful that those bytes may be registered multiple times if, and only if, the registrations happened under different paths within the named-file. |
| file |  | :manifest() | The Path from root to the file containing this information. |
| file_home |  | :manifest() | The path to the directory representing the original physical file registered and named by the same name, including extension. This directory holds the version files. The path is constructed using the [inputs] files key in config.ini. That means in some contexts, for e.g. FlightPath Server, it will always be fully qualified to the filesystem root. File homes are derived using a template, if one is provided in the registration method call or a default is configured for the named-file. |
| fingerprint |  | :manifest() | In most cases, the SHA256 hash of the bytes. The exception is: files in S3 are identified by MD5 hash because AWS calculates that for us, improving performance at the tiny risk of a hash collision. For our purposes, the MD5 is equally effective to the SHA256. |
| uuid |  | :manifest() | A UUID identifying the registration that this manifest entry represents. The UUID is typically generated by the Framework at registration-time; however, it is possible to submit a pre-created UUID with the registration method call. FlightPath Server does the latter so that it can regester files asynchronously. |
| time |  | :manifest() | The moment the registration occurred in UTC. |
| from |  | :manifest() | The source path of the original data file that is registered and copied into the named-file. This is the path segments data that the named-file's default template, or a template provided by the user at registration-time, uses to construct the path within the named-file. |
| mark | optional | :manifest() | The name of a worksheet in an Excel file. When there is a mark, the workbook as a whole is registered, using a fingerprint of the whole file for versioning purposes. However, the mark is captured so that when you ask for the named-file by name the Framework takes account of the mark and returns just the worksheet that is technically the data that was the target of the registration. The impact of this difference between fingerprint and worksheet content is expected to be low. It is possible that a worksheet might remain static between two attempted registrations, but data outside that specific worksheet changed, resulting in a new registration with a new fingerprint and UUID, but still asserting only the unchanged worksheet. |
| template |  | :manifest() | A string with braces-bracketed replacement tokens that determines the path within the named-file of the file home, where a registered file is stored. The replacement tokens are of two kinds: 1. the indexes of the path segments found in the origin path. E.g. :0 for the first directory below the root, :1 for the next path segment, and so on, and 2. tokens for elements of the current datetime, e.g. :day, :month, :year, etc. |

## 3. Named-Paths Manifest (per named-paths group)

`csvpath/managers/paths/paths_registrar.py` — one flat, append-only array per
named-paths group, one entry per loaded/reloaded version of the whole group.
This is the manifest `CsvpathsReferenceFinder3`/`:manifest()` actually reads
today.

| Field | Optional | References v3 Function | Description |
|---|---|---|---|
| archive_name |  | :manifest() | The `[results] archive` value from `config.ini` at the time the current version of the named-paths group was loaded. |
| named_paths_name |  | :manifest() | The named of this named-paths group. |
| named_paths_home |  | :manifest() | The path to the root directory of this named-paths group. The `[inputs] csvpaths` value from `config.ini`, the path to the root of all named-paths groups, is used to construct this path. |
| group_file_path |  | :manifest() | The path to the `group.csvpaths` file that contains all the csvpath statements in the group. Every named-paths group has this file. |
| source_path | optional | :manifest() | The path to the file or directory that housed the csvpath statements that make up the contents of the version of this named-paths group this entry represents. |
| named_paths |  | :manifest() | The full byte-for-byte text of the csvpath statements comprising this entry's version of this named-paths group. The value of this key can potentially be quite large. |
| named_paths_identities |  | :manifest() | A list of the identities of the csvpaths in this version of this named-paths group. Identities are the names given to csvpaths in their leading comments using standard metadata keys (:id, :Id, :ID, :name, :Name, :NAME; in that order of precedence) or, if a name is not found, the 0-based index of their position within the named-paths group. |
| named_paths_count |  | :manifest() | The number of csvpaths in this version of the named-paths group. |
| fingerprint |  | :manifest() | In most cases, the SHA256 hash of the `group.csvpaths` file. The exception is: files in S3 are identified by MD5 hash because AWS calculates that for us, improving performance at the tiny risk of a hash collision. For our purposes, the MD5 is equally effective to the SHA256. |
| time |  | :manifest() | The moment this version of the named-paths group was loaded. |
| time_started | optional | :manifest() | The beginning moment of the load. Loads are quick, so this is typically not very useful. |
| time_completed | optional | :manifest() | The end moment of the load. Loads are quick, so this is typically not very useful. |
| uuid |  | :manifest() | The unique identifier for this version of the named-paths group. |
| manifest_path |  | :manifest() | The path to this file. |
| template | optional | :manifest() | The default run dir template. A string with braces-bracketed replacement tokens that determines the path within the named-results of the run directory (typically referred to as the run dir), where results are stored. The replacement tokens are of two kinds: 1. the indexes of the path segments found in the origin path. E.g. :0 for the first directory below the root, :1 for the next path segment, and so on, and 2. tokens for elements of the current datetime, e.g. :day, :month, :year, etc. |

## 5. Results Run Manifest (per run)

`csvpath/managers/results/results_registrar.py` — a single dict inside each
run's own directory. This is the manifest `ResultsReferenceFinder3`/
`:manifest()` actually reads today for a selected run.

| Field | Optional | References v3 Function | Description |
|---|---|---|---|
| time |  | :manifest() | The moment this run started. |
| uuid |  | :manifest() | A UUID that identifies the specific metadata event. Not typically used for correlation. Should be considered deprecated. |
| run_uuid |  | :manifest() | The unique UUID assigned to this run. The CsvPaths instance generates this UUID without the triggering process or person having the opportunity to override it; however, a correlation key may be passed into the run, and stored with the run, for that purpose. |
| serial |  | :manifest() | True if the run completes csvpath statements serially, rather than completing a pass through all of them as each line is processed. |
| time_completed | optional | :manifest() | When the run completes this field is updated with the moment it ended. |
| all_completed | optional | :manifest() | True if all csvpath statements considered all lines to be scanned |
| all_valid | optional | :manifest() | True if all csvpath statements report they are valid. I.e. none were failed with `fail()` or due to a build-in validation error combined with a validation-mode setting of `fail`. |
| error_count | optional | :manifest() | The number of errors from all csvpath statements in the run. |
| all_expected_files | optional | :manifest() | True if all the files expected by files-mode in all the csvpaths in the named-paths group are present. There can be more than the number of files expected, for e.g. if a run outputs parquet files they won't be considered by files-mode. |
| status |  | :manifest() | The literal string `started` when the run begins, overwritten with the literal string `complete` (not `completed`) when it finishes. See `ResultsRegistrar.STARTED`/`ResultsRegistrar.COMPLETE` in `results_registrar.py`. |
| run_home |  | :manifest() | The run dir. I.e. the top level directory containing all the runs assets, which is named by the timestamp (disambiguated) of the moment it was run. |
| named_results_name |  | :manifest() | The name of the results this manifest describes. Usually the same as `named_paths_name`, but not guaranteed: if the run is invoked with a `$`-reference as the paths name, `complete_run()` in `results_manager.py` strips it down to `ReferenceParser(pathsname).root_major` for `named_results_name`, while `named_paths_name` keeps the raw reference string. The two can genuinely differ in that case. |
| named_paths_name |  | :manifest() | The name of the named-paths group that generated the run |
| named_paths_uuid |  | :manifest() | The UUID that uniquely identifies the version of the named-paths group that caused the results to  exist. |
| named_file_name |  | :manifest() | The name of the named-file this run took as it's data input. |
| named_file_uuid |  | :manifest() | The UUID that uniquely identifies the version of the named-file that was the data source for the run. |
| named_file_path |  | :manifest() | The path to the named-file version. |
| named_file_size |  | :manifest() | The byte size of the named-file version used, read from the filesystem at the moment the run started. Not actually optional: `register_start()` sets it unconditionally, alongside `named_file_fingerprint`. Falls back to `0` if the file cannot be found (`FileNotFoundError`), per `_size()` in `results_registrar.py`. |
| named_file_last_change |  | :manifest() | The last-modified timestamp of the named-file version used, read from the filesystem at the moment the run started. Not actually optional, same as `named_file_size` above. Falls back to `-1` if the file cannot be found, per `_last_change()` in `results_registrar.py`. |
| named_file_fingerprint |  | :manifest() | The fingerprint of the named-file version used as input to this run. |
| named_file_fingerprint_on_file |  | :manifest() | Deprecated. Do not use. |
| hostname |  | :manifest() | If available, the name of the computer where the process that performed the run was. |
| ip_address |  | :manifest() | Currently always null. `Metadata.__init__` (`csvpath/managers/metadata.py`) sets `self.ip_address = None` and the actual `socket.gethostbyname()` lookup that would populate it is commented out, because it was found to block for multiple seconds in some environments. The field exists for a future fix, not a working lookup today. |
| username |  | :manifest() | If available, the user owning the process that performed the run. |
| method |  | :manifest() | The run method is one of collect_paths, fast_forward_paths, next_paths, collect_by_line, fast_forward_by_line, next_by_line. Methods that include the suffix `_paths` run the csvpaths in the named-paths group serially one following the other, each starting from the top of the data. The methods with the suffix `_by_line` have each csvpath statement in the named-paths group consider each line before they all start again with the next line. The difference is usually not significant, but in some cases the difference in processing order allows for different desired outcomes. |
| manifest_path |  | :manifest() | The path to this manifest. |

## 8. Named-File Definition (definition.json, per named-file)

`csvpath/managers/files/file_descriptor.py` (Pydantic `Config`, via
`NamedFileDescriber`, `csvpath/managers/files/file_describer.py`) — a single
dict, stored at the same home directory as the Named-File Manifest
(table 1). Unlike manifest.json, this file is genuinely optional (a
named-file that was never explicitly configured has none on disk) and is
not versioned — one current definition regardless of which registered
version you are looking at. Field list derived directly from the Pydantic
model, not from a real on-disk example — the model's own `extra: allow` at
both levels means a real file could carry additional undeclared keys beyond
these. This is one of the two schemas `:definition()` (`DATATYPES =
(FILES, CSVPATHS)`) reads as a whole dict; there is no dedicated
single-field accessor for anything below yet.

| Field | Optional | References v3 Function | Description |
|---|---|---|---|
| template | optional | :definition() | Path template string for this named file. Same token syntax as the Named-File Manifest's own `template` field. |
| on_arrival | optional | :definition() | Object. Configures a run to be triggered automatically when a new version of this named-file arrives. Absent entirely if no arrival action is configured. |
| on_arrival.named_paths_group | optional | :definition() | The named-paths group to run when this named-file receives a new version. |
| on_arrival.run_method | optional | :definition() | The method to invoke on arrival, e.g. `collect_paths`. |
| sources | optional | :definition() | Object, keyed by an arbitrary source name chosen by whoever configured it. Each value is a `ServerConfig` (see below). Holds the credentials/target used to poll or reach a remote source for this named-file. |
| sources.\<name\>.address | optional | :definition() | Hostname or IP of the source, for the named source entry. |
| sources.\<name\>.port | optional | :definition() | Port number of the source. Coerced from a numeric string if needed. |
| sources.\<name\>.username | optional | :definition() | Login username for the source, may itself be an env-var name rather than a literal value. |
| sources.\<name\>.password | optional | :definition() | Login password for the source, may itself be an env-var name rather than a literal value. |

## 9. Named-Paths Definition (definition.json, per named-paths group)

`csvpath/managers/paths/paths_descriptor.py` (Pydantic `Config`/`GroupConfig`,
via `NamedPathsDescriber`, `csvpath/managers/paths/paths_describer.py`) — a
single dict, stored at the same home directory as the Named-Paths Manifest
(table 3). On disk the whole thing is nested one level deeper than the
Pydantic model names suggest: the real top-level JSON key is `_config`
(`NamedPathsDescriber.CONFIG`), holding a `Config` whose `groups` is a dict
keyed by named-paths name, each value a `GroupConfig` with the fields below.
Same optional/not-versioned caveats as table 8. This is the other schema
`:definition()` reads as a whole dict; again, no dedicated single-field
accessor exists yet.

| Field | Optional | References v3 Function | Description |
|---|---|---|---|
| template | optional | :definition() | The default run-dir template for this named-paths group. This is the actual source of truth read by `PathsManager.get_template_for_paths()` at load time — the Named-Paths Manifest's own `template` field (table 3) is a snapshot of whatever this held at that particular load, not an independently-set value. The two can only diverge if this is edited after a version was already loaded. |
| scripts | optional | :definition() | Object. Filenames of scripts to run for each of four completion states, stored alongside `group.csvpaths` in this named-paths group's home directory. |
| scripts.on_complete_all | optional | :definition() | Script run regardless of outcome. |
| scripts.on_complete_valid | optional | :definition() | Script run only if the csvpath statement is valid. |
| scripts.on_complete_invalid | optional | :definition() | Script run only if the csvpath statement is invalid. |
| scripts.on_complete_error | optional | :definition() | Script run only if the csvpath statement has errors. |
| webhooks | optional | :definition() | Object. Same four completion states as `scripts`, each firing an HTTP call instead of a script. |
| webhooks.on_complete_all/on_complete_valid/on_complete_invalid/on_complete_error | optional | :definition() | Each is an object: `url`, `payload`, and `headers` (a list of `{name, value}` pairs). |
| transfers.path_transfers | optional | :definition() | Object, keyed by csvpath identity or index within the group. Each value declares transfers for the same four completion states as `scripts`/`webhooks`, but as a list of `{file, transfer_to}` per state rather than a single value. This is the descriptor-based transfer mechanism referenced in issues #224 and #226 — `on_complete_invalid` and `on_complete_error` here are accepted by the schema but, per #226, never actually triggered at runtime. |
| destinations | optional | :definition() | Object, keyed by an arbitrary destination name. Each value is a `ServerConfig` (`address`, `port`, `username`, `password`) — same shape as table 8's `sources`, but for where this group sends things rather than where a file is polled from. |
